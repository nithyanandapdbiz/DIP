### 3.3 Naming finding (corrects EPIP-001 M-1 — reconciled against disk)

**EPIP-001 stated both planes expose a command literally named `functionaltest`. Disk shows otherwise, and the correction matters:**

- **IP** exposes **`functionaltest`** (execution-**request** orchestration; launches no browser).
- **EP** exposes **`functional`** (local **execution**; launches the browser).

These are **different strings — there is no literal collision.** The real risk is **semantic**: the token `functionaltest` (which the architecture's intent associates with EP execution) currently lives on the IP as an *orchestration* command, while the EP's *execution* command is `functional`. A reader scanning names can misread "the IP has `functionaltest`" as "the IP executes tests" — which is precisely the misconception GOVERNANCE-EPIP-001 was launched to investigate.

**Recommended naming strategy (preserves backward compatibility; not implemented — a rename is a product/DX behaviour change, out of this mission's scope):**

| Command | Keep (compat) | Recommended clarifying alias / doc |
|---|---|---|
| IP `functionaltest` | Yes | Document as *"request functional execution (orchestration → EP)"*; optionally add alias `functionaltest:request` pointing at the same launcher |
| EP `functional` | Yes | Document as *the* canonical EP execution entry point; optionally add alias `functionaltest` **only if** the IP command is simultaneously disambiguated, to avoid re-introducing a cross-plane literal collision |
| `test` (both) | Yes | Distinct meanings (IP unit vs EP Playwright); low ambiguity — no action |

The single de-ambiguation that removes the misconception without any rename: **the architecture ownership doc explicitly names both commands and their planes** (delivered in §5 below).
