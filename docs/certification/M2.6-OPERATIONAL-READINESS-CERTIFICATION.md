### Why the mutual-TLS evidence is worth trusting

The gateway is not asked whether it would refuse an unauthorised client. **A real client connects over a real TLS socket, and the question asked is whether a response was served.**

That framing is deliberate and was arrived at by getting it wrong first. Under TLS 1.3 the client sends its certificate *after* the server's Finished message, so a client the server will reject still observes its own handshake succeeding. Asserting on `secureConnect` would have let a forged certificate look accepted. **"Was a response served?" is the only signal that cannot be fooled this way** — and the first version of the test, which asserted on the handshake, hung rather than passed, which is how the flaw surfaced.

The certificates are genuine X.509 issued by OpenSSL, and a leaf is verified against the root using **Node's own `X509Certificate.verify()`** rather than this codebase's logic. A certificate only our own validator accepted would prove nothing.

### Two design choices worth recording

**Tenant identity is bound in the certificate, not alongside it.** The tenant appears in the subject CN *and* in a SAN URI (`urn:dbiz:tenant:<id>`). Every authorisation decision derives from the presented certificate; a `tenantId` supplied in the request body is treated as an attack and answered `403` with an audit record.

**Rotation overlaps; revocation ends it.** The previous certificate stays valid until explicitly revoked. An atomic swap would force the customer to restart in lockstep with DBiz — which R-19.11 forbids — so overlap is what makes rotation possible without a redeploy. Revocation is enforced at the gateway rather than in the TLS trust store, so it takes effect without reissuing the CA.

## 5. Defects found, and fixed

| # | Defect | How found | Fix |
|---|---|---|---|
| **1** | The end-to-end mTLS test **hung** instead of failing | A rejected client's promise never settled — no `close` handler | Rewritten around "was a response served?", with a wall-clock watchdog. An idle timer is reset by the very alert bytes that signal rejection, so `socket.setTimeout` could fail to fire at all |
| **2** | The operational gate's anti-erosion list still named **four** properties | Reviewing the gate after adding twelve | The list now names all twelve, plus a check that the seven runtime properties specifically were proven |
| **3** | The scorecard counted tests in **`@dbiz/contracts` only** | Reported 58 when 140 pass | It now enumerates every package with a built test tree, and refuses to skip one whose suite cannot be read |
| **4** | `verify-governance-self-validation` kept **one proof per gate** | Adding a second fault for the operational gate | Proofs are grouped, and every proof for a gate is audited |

**Defect 3 is the instructive one.** A scorecard that undercounts looks conservative and is in fact wrong: it had silently stopped describing the platform, and would have hidden any regression in the two packages it had forgotten.

## 6. The gate can detect a gateway that stops refusing

The operational gate now carries **two** fault proofs. The second is the sharpest question that can be asked of this milestone's evidence:

> If the API gateway stopped refusing unauthorised callers, would governance notice?

The recorder replaces the runtime's built entry point with one whose gateway answers `200` to everything — no client certificate required — runs the gate, and observes the result. **The gate failed and named the cause.** The original bytes are snapshotted and restored.

The fault targets build output deliberately. A probe planted in source or in the lockfile makes the recorder a source of the defect it exists to detect; that has happened here once already, and the snapshot-and-restore discipline is the lesson from it.
