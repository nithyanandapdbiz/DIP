# M2.7 Certification — Customer Success Readiness

**Programme:** DBiz Agentic QA Platform · **Phase:** P2 / M2.7
**Date:** 2026-07-22 · **Constitution:** v1.3 · **Baseline:** M2.6 (commit `de80bf2`)
**Authority:** Enterprise Certification Authority

**Status: CERTIFIED WITH FOUR DECLARED EXCEPTIONS.** Fifteen customer readiness properties are proven by executing the customer journey. Four are `NOT MEASURED`, each with a named blocker. **None was simulated.**

---

## 1. The finding this milestone exists for

**Five of the six declared supported targets were declared-but-unbuilt.**

The solution generator emitted TypeScript sources for every language in the supported registry. A customer selecting `python` received `register.ts`. A customer selecting `java` received `register.ts`. No `pom.xml`, no `requirements.txt`, no `.csproj` — and a file *count* could not see it, because the count was identical.

This is the platform's characteristic failure — R-11.2, declared-but-unbuilt — applied to its own compatibility claims, and it is precisely what **C-25.8** exists to catch: *"a target declared supported without a validation run is declared-but-unbuilt."*

**The registry was not narrowed to hide it.** Withdrawing support the moment it is measured is a different way of avoiding the work. The targets are declared, so they were built: each language now emits its own sources, its own dependency manifest, its own test layout and a base image matched to its runtime.

| Language | Emits | Manifest | Base image |
|---|---|---|---|
| TypeScript | `.ts` | `package.json` | `node:24-alpine` |
| JavaScript | `.js` | `package.json` | `node:24-alpine` |
| Python | `.py`, `conftest.py`, `pytest.ini` | `requirements.txt` | `python:3.12-slim` |
| Java | `.java` under `src/main/java/com/dbiz/execution` | `pom.xml` / `build.gradle` | `eclipse-temurin:21-jre-alpine` |
| C# | `.cs` | `ExecutionPlane.csproj` | `mcr.microsoft.com/dotnet/sdk:8.0-alpine` |

A Java solution on a Node base image is a solution that cannot start, and it would have looked correct in every review.

### Why the error catalogue can be trusted

It is not written from the gateway's source. The scenario **provokes** each refusal — calling with no certificate, no token, an unauthorised path, an asserted tenant, a stolen token — and documents what came back. A status the gateway was never observed to return does not appear, and a test asserts that: documenting a `429` the platform never sends is a promise nobody keeps.

## 3. What is NOT MEASURED

| # | Property | Blocker |
|---|---|---|
| **K-12** | A customer completes onboarding in under 30 minutes | **No customer has been observed.** The automated path is measured (K-1); the human path — reading, deciding, obtaining approvals — has no observation and is not modelled |
| **K-13** | Generated example test suites execute successfully | Playwright, Selenium, JUnit, NUnit and pytest are not installed here. Scaffolding is generated and validated; running a customer suite is not |
| **K-14** | Installation validated on a clean environment for every target | Requires a clean-environment runner per language (C-25.1, R-25.6) |
| **K-15** | Deployment guides reproduce successfully | Docker unavailable — the same blocker as operational E-2 |

**K-12 is the one worth reading carefully.** The brief asked to *"verify customer can onboard in under 30 minutes"*. What can honestly be measured is the automated path, and it is: 186ms across seven steps. What cannot be measured without a customer is a customer. Reporting 186ms as "onboarding takes under 30 minutes" would be true and misleading at once — the 30 minutes is dominated by the reading and deciding this milestone can only make shorter, never observe.

### Two design decisions worth recording

**Onboarding is not finished when credentials are issued — it is finished when a call using them is served.** The seventh step verifies an authenticated call. Anything less leaves the customer to discover the failure themselves, later, in their own pipeline.

**Validation happens before creation.** A tenant created against an unbuildable profile leaves the customer holding an identity for a solution that will never generate, and unwinding that is a support case rather than a retry.

## 5. Defects found, and fixed

| # | Defect | How found | Fix |
|---|---|---|---|
| **1** | **Five of six declared supported targets emitted the wrong language** | Generating for every combination in the registry and looking at the file names | Per-language emitters; K-2 now gates it |
| **2** | The Customer Success Package was **not deterministic** | K-8.d, comparing two builds | A measured wall-clock duration was being rendered into documents. It describes the **run**, not the **release** — moved to the manifest |
| **3** | The authentication guide carried a **JWT-shaped literal** | K-9, the platform's own credential scan | Replaced with a named placeholder. A realistic-looking token reads as a credential to every scanner and teaches a reader nothing |
| **4** | `.env.example` would be flagged as a **retained secret file** by the platform's own non-retention scan | E-5, after the package landed under `docs/` | Renamed to `env.example`. Loosening a security scan so documentation can use a familiar filename trades a real control for a cosmetic one |
| **5** | The recorder left evidence claiming a **content hash for a package it refused to publish** | Investigating an intermittent gate failure | The hash is recorded only when the package is actually written |

**Defect 2 is the instructive one.** It produced an intermittent gate failure that did not reproduce on demand, and the temptation was to record it as a flake. It was not a flake: a duration rendered into a document made the package differ between builds, so a customer could not verify they held what was published. The property that caught it — *two builds of the same release are byte-identical* — was written in the same session, for exactly this reason.

## 6. A boundary test that was broader than its criterion

`C-03.14` states: *"Intelligence Core does not depend on Platform Core."* Its test asserted that **no** workspace package imported Platform Core.

Those were the same assertion while only one other package existed. Once Customer Success — a **Platform Service** under ADR-0018, not Intelligence Core — legitimately needed the generator, they diverged, and the test failed for a package it was never written to forbid.

**The test was not relaxed to fit the new code.** It now enforces the criterion (Intelligence Core must never import Platform Core) *and* keeps a stricter allowlist, so any future importer must be admitted deliberately, in one place, with a stated reason. An allowlist fails closed; a denylist of Intelligence Core names would fail open the first time one was named something unanticipated.

## 7. One item in the brief that is not supported

The brief's Workstream 5 lists **WebdriverIO** among the targets to validate. WebdriverIO is **not in the supported registry**, and the brief's own rule applies to it:

> *No unsupported technology may appear in customer documentation.*

It therefore does not appear in the compatibility matrix, the examples, or any generated guide. Adding it is a roadmap decision — extending the registry and the emitters — not a documentation change. Recorded here rather than quietly satisfied.
