# ADR-0063 — SBOM is a Build Artifact, Not Repository Source

**Status:** Accepted
**Date:** 2026-07-30

---

## 1. Problem

The CycloneDX SBOM at `governance/supply-chain/sbom.cdx.json` was committed to the
repository and tracked in Git. A generated inventory checked into source control is
a stale claim the moment the dependency tree moves: two truths then exist — the
committed file and the tree the generator would resolve now — and nothing forces
them to agree between the commit that wrote the file and the next one that touches
dependencies. Worse, an out-of-band consumer could read, publish, or **attest** the
committed copy, signing provenance over inventory that no build ever produced.

## 2. Context

Two facts already on disk decide this:

- **The generator is authoritative, the file is not.** `verify-supply-chain.js` §1
  regenerates the SBOM on every run and then asserts it "was produced by this run,
  not left behind" (rejecting any file older than the gate start). The every-commit
  governance gate therefore already treats the committed file as untrusted — it
  overwrites it before reading it. The committed copy earned no trust; it only
  carried risk.
- **The SBOM is derived, not authored.** `generate-sbom.js` builds the component set
  from `pnpm licenses list` over the *resolved* tree — the lockfile and installed
  packages — never from `package.json`. Its output is a pure function of the
  lockfile plus the resolver, which is the definition of a build output.

The repository stores **source**: generators, verification logic, governance
policies, schemas, validation rules. Generated outputs are **evidence**, produced
during a gate run or a CI/CD build. The SBOM was miscategorised as the former.

## 3. Alternatives

1. **Keep committing the SBOM and add a gate that diffs committed-vs-regenerated.**
   Rejected: adds a second source of truth and a whole failure mode (drift alarms)
   to protect a file that has no reason to be in the repository at all. Solves a
   problem created only by committing it.
2. **Keep the file but attest it in CI anyway.** Rejected: this is the exact defect —
   attesting a committed artifact signs provenance over bytes no build produced.
3. **Treat the SBOM as a build artifact: generate per build, never read from Git,
   never commit.** Chosen. Removes the second source of truth and aligns the file's
   lifecycle with what it actually is.

## 4. Decision

The SBOM is a build artifact governed by a single rule, now a supply-chain standard:

> **Generated artifacts must never become repository source.** Repository contents
> represent source. Generated outputs represent evidence. Evidence is produced
> during a gate run or CI/CD, consumed in the same run, and never committed.

Concretely:

- `governance/supply-chain/sbom.cdx.json` is **removed from version control** and
  added to `.gitignore` (after the `!governance/**` guard, so the ignore wins).
- The SBOM is **generated on every workflow execution** and every gate run.
- Provenance **signs the generated artifact only**, handed job-to-job as an uploaded
  build artifact — never a Git checkout of a committed file.
- Supply-chain verification consumes the **freshly generated** SBOM (unchanged:
  `verify-supply-chain.js` already regenerates before reading).
- The repository keeps only the **generation and verification logic**.

## 5. Consequences

- No stale SBOM can ever be committed or attested; provenance now covers exactly
  what CI built and scanned.
- One source of truth: the generator. Drift between a committed file and the
  resolver is structurally impossible.
- A fresh checkout has no SBOM until a gate or build produces one. Consumers must
  tolerate its absence before first generation — `generate-matrices.js` already
  does (`filter(existsSync)`), listing the SBOM as evidence only once present.
- CI must install the resolved tree before generating, because the SBOM is derived
  from resolution, not declaration. The `scan` job now runs
  `pnpm install --frozen-lockfile` first.
- **Generalised evidence audit (2026-07-30, executed).** The follow-up this ADR
  named — `governance/supply-chain/evidence.json` — was audited alongside every other
  committed generated artifact and resolved under the same standard. 55 generated files
  were untracked (`git rm --cached`, working copies kept) and ignored: 51 `evidence.json`
  (all `verify-*.js` regenerate their own and refuse a stale one, R-14.2), both
  traceability matrices (regenerated by `verify-traceability` → `generate-matrices.js`),
  `packages/contracts/compat/evidence.json` (regenerated by `verify-contract-compatibility`),
  and the two engineering reports (`ENGINEERING_SCORECARD.md`, `PLATFORM_MATURITY.md`).
  Two files that are *read as inputs and never regenerated in-run* were confirmed as
  **source and KEPT**: `governance/verification/proofs.json` (fault-injection registry,
  regenerated only by the manual `record-fault-proofs.js`, read by six gates) and
  `governance/closure/baseline.json` (programme-closure baseline, written by no code,
  read by eight gates). CI (`run-all.js`) already regenerates all evidence in-process and
  consumes it there, so nothing read a committed copy; `ci.yml` now also uploads the
  produced evidence as a build artifact.

## 6. Migration strategy

Executes only after ACCEPTED:

1. `git rm --cached governance/supply-chain/sbom.cdx.json` — untrack, keep the
   working copy so in-run consumers are uninterrupted. *(done)*
2. Add the ignore rule after the `!governance/**` guard in `.gitignore`. *(done)*
3. Add `corepack enable && pnpm install --frozen-lockfile` before `generate-sbom.js`
   in the `supply-chain` workflow. *(done)*
4. Confirm provenance consumes the uploaded artifact, not a checkout. *(done — the
   `provenance` job downloads the `sbom` artifact and attests `sbom/sbom.cdx.json`)*
5. No consumer reads the committed file: `verify-supply-chain.js` regenerates;
   `generate-matrices.js` guards with `existsSync`; ADR-0033 only references it
   descriptively. *(verified)*

No data migration is required — the artifact is reproducible from the lockfile.

## 7. Version impact

Additive and non-breaking to source. No package version change. The published
provenance subject is unchanged in shape; only its origin moves from a Git checkout
to a build artifact. Consumers of the repository that expected a committed SBOM must
generate it (`node governance/supply-chain/generate-sbom.js`) — this is the intended
behaviour change.

## 8. Affected components

- `.gitignore` — ignore rule for `governance/supply-chain/sbom.cdx.json` (post-guard).
- `governance/supply-chain/sbom.cdx.json` — removed from version control.
- `.github/workflows/supply-chain.yml` — frozen install before generation; provenance
  attests the uploaded artifact.
- `governance/supply-chain/generate-sbom.js` — unchanged; remains the sole source of
  the SBOM.
- `governance/verification/verify-supply-chain.js` — unchanged; already regenerates.
- `governance/traceability/generate-matrices.js` — unchanged; already `existsSync`-guarded.

Generalised evidence audit (2026-07-30) additionally affected:

- `.gitignore` — ignore rules for `governance/**/evidence.json`, `governance/**/*-evidence.json`,
  the two traceability matrices, `packages/contracts/compat/evidence.json`, and the two
  engineering reports (all after the guards; scoped to exclude the baselines below).
- 55 generated artifacts — removed from version control (`git rm --cached`, working copies kept).
- `.github/workflows/ci.yml` — regenerates the scorecard and uploads all produced evidence +
  reports as a `governance-evidence` build artifact (`always()`).
- **KEPT as source** (read as inputs, never regenerated in-run): `governance/verification/proofs.json`,
  `governance/closure/baseline.json`; and hand-authored `program/MULTITENANCY_REVIEW/08_COMPLIANCE_MATRIX.md`.
