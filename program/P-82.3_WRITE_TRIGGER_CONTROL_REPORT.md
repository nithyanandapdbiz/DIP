# P-82.3 — is a write-trigger control constructible?

**2026-08-06. Reported before ADR-0082 §6 step 1, as required. Nothing built.**

> **YES — AND THE CONSTRUCTIBLE FORM IS STRONGER THAN THE ONE ASKED FOR, BECAUSE THE ASKED-FOR ONE
> COUNTS THE WRONG THING.**
>
> The instruction was *"a gate asserting the store has exactly those two call sites."* **A call-site
> count is the weaker half and, pinned as a number, is a defect this CHARTER already names.** What
> makes a delivery record a delivery record is **which event causes the write** — so the primary
> control is the store's **write surface naming its two events and admitting no third**, and the
> gate becomes a **permitted-caller census** rather than a count.
>
> **It lands with the store as P-82.9.** And ADR-0082 states what it does **not** cover, because a
> residual stated is honest and a residual implied covered is what this report exists to prevent.

---

## 1. The gap, restated exactly

**The allow-list (P-82.6) enumerates FIELDS. P-82.3 governs CAUSATION. They do not overlap.**

A diagnostic field could be added **to** the allow-list by someone reading it as a schema rather than
as an authorisation — the enumeration would grow by one line, every gate would stay green, and the
store would begin recording when a package was fetched. **Nothing in ADR-0082 as drafted would stop
it**, and P-82.3 would be a rule with no enforcement sitting beside a list that looks like it covers
it.

**The distinction that matters:** a delivery record and an evidence record can hold **identical
fields** and differ only in **what causes a row to be written.**

## 2. Why "exactly two call sites" is the wrong assertion, though the instinct is right

**Pinning a count is CHARTER §17.1(i)'s trap.** *Every count, ratio or population in a verdict line
is computed from what the run observed, or it is not printed* — and a gate whose passing condition is
the literal `2` must be **edited** whenever legitimate structure changes. A gate that people edit to
make green is a gate people edit to make green.

**And the count is not the property.** Two call sites into a general `record()` method is *worse* than
five call sites into `onEvidenceArrived`, because the first tells you nothing about what caused any
of them.

> **The property is: WHICH EVENTS may cause a write, and WHICH MODULES may assert them.**

## 3. The three candidate mechanisms, and what each actually catches

| # | Mechanism | Catches | Blind to |
|---|---|---|---|
| **A** | **Event-named write surface** — the store exposes `onPackageSealed(...)` and `onEvidenceArrived(...)` and **no general `record()`** | **A third EVENT.** A diagnostic write has no method to call; adding one is an API change, visible in the diff and requiring an ADR amendment | a caller that invokes an existing method **for the wrong reason** |
| **B** | **Permitted-caller census** — a gate asserting each write method is called only from its declared module | exactly B's blind spot: `onEvidenceArrived` called from a retrieval handler | **aliasing and dynamic dispatch** — `const f = store.onEvidenceArrived; f(...)` |
| **C** | **Module-private brand** — the write method requires a token only the triggering module can mint (`stages.ts`'s `SEAL` pattern) | construction of a trigger outside its module | **nothing, within one package — but it does not survive the package boundary**, §4 |

**A and B compose; C does not apply here.** A closes the cheap path, B closes A's blind spot, and B's
own blind spot is bounded by A — see §5.

## 4. Why the brand pattern does not transfer, stated so nobody reaches for it

`stages.ts` makes a stage result unconstructible outside its module with a **module-private symbol**:
*"a stage result carries a symbol that cannot be obtained outside this module, so no literal, cast or
spread can produce one."* It is the strongest mechanism in this platform.

**It does not reach this case.** The store lives in `@dbiz/platform-providers`; the two triggering
modules live in `@dbiz/tenant-onboarding-engine` and the functional-testing engine. **A token the
triggering modules can mint must be exported across the package boundary — and once exported, any
module can import the minting function.** The brand would look like enforcement and be a naming
convention.

**Recorded because it is the first thing a reader who knows `SEAL` will propose.**

## 5. The constructible control, in the form it should be built

**A — the write surface is the enumeration of events.**

Two methods, each named for its cause. **No `record()`, no `write()`, no `put()`, and no options bag
carrying an event discriminator** — a `kind: 'fetch'` parameter is a third event wearing a field's
clothes, which is precisely the move §1 describes.

**B — the gate asserts the PERMITTED CALLER SET, derived and declared.**

For each write method: the set of modules containing a call is computed from source, and compared
against a declared set of exactly the modules ADR-0082 authorises. **Not a count.** A new module
calling either method turns the gate red **on the day it is added**, naming the module and the
method — the shape `verify-composition-root.js` already uses, and the measurement D-122 performed by
hand when it established that `put` had zero non-test call sites.

**Tests are excluded and the exclusion is declared**, exactly as D-122's census excluded them; a test
suite legitimately drives both events.

**The fault proof is straightforward and is a completion condition:** add a call from a third module,
observe the gate RED naming that module, remove it, observe green — a clean → faulted → clean triple,
faulting the source of truth, with the branch that fired recorded.

## 6. THE REACH, STATED — because an unstated reach is the defect this session already recorded twice

> **A syntactic caller census cannot see an aliased or dynamically-dispatched call.**
> `const f = store.onEvidenceArrived; f(ref)` from a fourth module is invisible to B.

**A bounds that blind spot rather than leaving it open, and this is the argument for building both:**
an aliased call to `onEvidenceArrived` **still asserts that evidence arrived.** To record a fetch, a
caller must invoke a method whose name says evidence arrived, **at a point where no evidence
arrived** — a deliberate lie about the event, in a diff, under a method name that contradicts it.

**That is categorically different from adding a field to an allow-list**, which is the failure this
report was asked about: a plausible, well-intentioned, one-line change that no reviewer would query.
**The control does not make P-82.3 unbreakable. It makes breaking it require an act that cannot be
mistaken for routine.**

**What remains uncovered, and ADR-0082 must say so:**

1. A caller that **lies about the event** — invokes `onEvidenceArrived` where no evidence arrived.
2. **Aliased or dynamically-dispatched** calls, invisible to B (bounded by 1's visibility, not removed).
3. A **future maintainer widening the declared caller set** to make the gate green — the same failure
   mode as any allow-list, one level up. **The declared set is small and its entries are named in the
   ADR**, so widening it is an ADR amendment rather than a config edit.

## 7. Recommendation

**BUILD IT, as P-82.9, landing with the store.** A and B together, tests excluded by declaration, the
fault proof as a completion condition.

**And amend ADR-0082 to state the residual (§6) explicitly.** The instruction's own standard applies
and is the reason this report exists:

> **An unenforced discriminator stated as unenforced is honest; one implied to be covered by the
> allow-list is not.** P-82.3 is now **enforced in part** — and the part that is not enforced is
> named, rather than left to be inferred from a gate's existence.

## 8. What this does not change

P-82.6's allow-list is unaffected and still necessary: it governs **what is stored**, and P-82.9
governs **why a row exists**. Neither substitutes for the other, and the reason they were confusable
is that both are enumerations — **which is the observation that produced this report.**
