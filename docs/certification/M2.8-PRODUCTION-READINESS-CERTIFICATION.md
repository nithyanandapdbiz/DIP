## 1. The headline, stated before anything else

**This platform is not certified for General Availability, and nothing in this record should be read as certifying it.**

The mission asked to *"certify the platform for unrestricted production deployment"*. That cannot be done, for one reason: **nothing has ever been deployed.** Docker is unavailable in this environment, so E-2 has been `NOT MEASURED` since M2.5 and still is. Every measurement in this milestone was taken in-process, on one machine, and **no in-process measurement is evidence about a deployed system.**

Issuing a GA certificate on this evidence would be the most expensive false claim this programme could make — it is the one a customer would act on.

What M2.8 does establish is narrower, and worth having:

> **When this platform runs, its health is observable, its failures are diagnosable, its releases are verifiable, and every tenant is visible on its own.**

## 2. Two defects found by measurement, not review

### Tokens did not survive a restart

The token signing key was generated per process. A restarted instance rejected every token the previous one had issued, with `bad-signature`. **A routine deploy was a customer outage**, and no test before M2.8 could see it because none had ever restarted the platform.

Fixed by loading the key from state — **the same custody model the certificate authority already used for its root key**, applied to the second key rather than a new scheme invented under delivery pressure.

### Replay protection did not hold across instances

Nonces were held in a per-process map. Document 17 declares the Intelligence Plane *"multiple per region, horizontally scaled"*, and R-16.19 requires horizontal scalability without coordination. So a nonce refused by one instance was **accepted by another — no restart required, a load balancer was sufficient.** That is a replay window against C-08.22, produced by an assumption the code made silently.

The store is now injectable, the platform reports `replayProtectionIsSingleProcessOnly`, and readiness reports `degraded` while the default is in use. **Supplying a shared implementation is a deployment obligation**, recorded as debt **D-003** — where that store lives is a deployment-topology decision belonging to an ADR against document 17, not something to invent here.

### How the second was nearly missed

The first version of the restart scenario asserted only that the replayed request was **refused**. It was — with `bad-signature`, because of the *first* defect. **A refusal for an unrelated reason is a false pass**, and it was concealing a real replay exposure.

Asserting on the **reason** rather than the status is what exposed both. That is the transferable lesson of this milestone.

### Three design decisions worth recording

**Silence is `unknown`, never `healthy`.** A platform with no errors because it is serving no requests is not healthy. This is C-24.7, and it is the property most easily lost — every convenience (a default of zero, an average that skips nulls, a value carried forward) quietly converts *unmeasured* into *fine*.

**Telemetry refuses customer content rather than redacting it.** Redaction is a guess about which fields matter and fails silently when the guess is wrong. Refusal surfaces the mistake while someone is still looking at it.

**The intelligence service observes and never acts.** C-24.9 forbids remediation, and a **source scan** enforces it — not a comment, because the pressure to close the loop arrives during an incident, which is exactly when a comment stops working.

## 6. A modelling error, and what it cost

The first version of the operational run counted **every** refusal that was not a `403` as an availability failure. Refusing a replayed nonce or a stolen token therefore drove the gateway SLI down, and **the tenants the platform had just protected were reported as degraded**.

*Unexpected* means the platform failed, not that it refused. Only an unrecognised refusal now counts against availability — which is also why the classifier returns `unclassified` rather than guessing at the nearest category.

Left unfixed, this would have produced a permanently amber availability metric that operators learned to ignore, which is how an objective becomes decoration.

## 7. The gate can detect a health check that lies

The production gate carries a fault proof that replaces the health monitor with one reporting `healthy` whenever its dependencies are up, ignoring whether anything reported at all.

> If this platform started reporting green during a total outage of whatever reports to it, would governance notice?

**It does.** The gate fails and names the cause. If it did not, C-24.7 would be decorative and every dashboard in this milestone would be worth nothing.

The gate also checks **the claim itself**: that `certificationStatus` has not quietly become `certified`, that the `generalAvailability` field still says `NOT CERTIFIED`, and that the deployment gap G-1 is still reported. The most likely route to a false claim here is not a broken measurement — it is a passing measurement rounded up in a summary.
